## 1. Repository Overview

The workspace contains **two distinct sub-projects** that operate independently but are tightly coupled at the data level:

| Sub-project | Path | Role |
|---|---|---|
| **IMPACT (React UI)** | `src/` + project root | A Vite + React 19 single-page application that lets engineers describe a proposed code change and see its projected impact on the ShopFlow backend. |
| **ShopFlow Demo API** | `shopflow-demo/` | A standalone Node.js/Express REST API that acts as the *analysis target* — the backend whose change impact the IMPACT UI reasons about. |

These two sub-projects share no runtime code. The React app only reads ShopFlow's structure through static data files (`changeScenarios.js` loads `shopflow-demo/docs/change-impact-ground-truth.json` at build-time). Neither project imports from the other at runtime.

### 4.8 ShopFlow — Routes (`shopflow-demo/src/routes/`)

**Responsibility:** Define Express `Router` instances. Compose request validation middleware and `requireAuth` (on protected groups) before wiring controller handlers.

| Route file | Prefix | Auth-protected | Validation applied |
|---|---|---|---|
| `authRoutes.js` | `/api/auth` | No | `validateBody` on register + login |
| `userRoutes.js` | `/api/users` | Yes (`router.use(requireAuth)`) | `validateBody` on PUT /me |
| `productRoutes.js` | `/api/products` | No | `validateIdParam` on /:id |
| `orderRoutes.js` | `/api/orders` | Yes | `validateBody` on POST, `validateIdParam` on /:id |
| `paymentRoutes.js` | `/api/payments` | Yes | `validateBody` on POST, `validateIdParam` on /:id and /:id/refund |

**Depends on:**
- Respective controller (e.g., `authController.js`)
- `src/middleware/authMiddleware.js` (protected routes)
- `src/middleware/validationMiddleware.js`

**Depended on by:**
- `shopflow-demo/src/app.js`

### 4.10 ShopFlow — Services (`shopflow-demo/src/services/`)

**Responsibility:** Domain logic — validation, orchestration, error surfacing. This is where cross-domain calls happen.

| Service | Key responsibilities | Cross-service dependencies |
|---|---|---|
| `authService.js` | Hash password (bcrypt), check duplicates, issue JWT | `userModel`, `utils/jwt.js` |
| `userService.js` | Fetch profile, update name/email with duplicate check | `userModel` |
| `productService.js` | List products, fetch by ID, reserve stock | `productModel` |
| `orderService.js` | Validate user, price items, run inventory+order SQLite transaction, prepare payment intent | `userService`, `productService`, `orderModel`, `paymentService.preparePayment`, `config/database.js` (transaction) |
| `paymentService.js` | Verify ownership, process/refund via mock provider, update payment + order status | `orderModel`, `paymentModel`, `mockPaymentProvider` |

**Depends on:** Models, `utils/errors.js`, `utils/jwt.js` (authService), `config/database.js` (orderService), `mockPaymentProvider` (paymentService).

**Depended on by:** Respective controller; `orderService` also calls `paymentService.preparePayment`.

### 4.11 ShopFlow — Models (`shopflow-demo/src/models/`)

**Responsibility:** All SQLite queries. Obtain the shared connection from `config/database.js`. Map raw row objects to domain-facing objects (e.g., cents → decimal price).

| Model | Tables accessed | Key operations |
|---|---|---|
| `userModel.js` | `users` | `create`, `findByEmail`, `findById`, `update` |

| `orderModel.js` | `orders`, `order_items` | `create` (order + items), `findById`, `findByUserId`, `updateStatus` |
| `paymentModel.js` | `payments` | `create`, `findById`, `findByOrderId`, `updateStatus` |

**Depends on:** `src/config/database.js` (all four).

**Depended on by:**
- `userModel` → `authService`, `userService`
- `productModel` → `productService`
- `orderModel` → `orderService`, `paymentService`
- `paymentModel` → `paymentService`

### 4.12 ShopFlow — Middleware (`shopflow-demo/src/middleware/`)

**Responsibility:**

| File | Responsibility |
|---|---|
| `authMiddleware.js` | `requireAuth` — extracts `Authorization: Bearer <token>`, calls `verifyToken`, attaches `{ id, role }` to `request.user`; throws `AppError(401)` on failure |
| `validationMiddleware.js` | `validateBody(fields)` — schema-style body validator; `validateIdParam` — ensures `:id` is a positive integer; helper predicates `isEmail`, `isPositiveInteger` |
| `errorMiddleware.js` | `notFoundHandler` (404 fallback) and `errorHandler` (maps `AppError` to status code, 500 → generic message) |

**Depends on:**
- `authMiddleware.js` → `src/utils/jwt.js`, `src/utils/errors.js`
- `validationMiddleware.js` → `src/utils/errors.js`
- `errorMiddleware.js` → `src/utils/errors.js`

**Depended on by:**
- `authMiddleware.js` → `userRoutes`, `orderRoutes`, `paymentRoutes`
- `validationMiddleware.js` → all five route modules
- `errorMiddleware.js` → `src/app.js`

### 4.13 ShopFlow — Database Layer (`shopflow-demo/src/config/` + `src/db/`)

**Important files:**

| File | Role |

**Depends on:** `better-sqlite3` (external), Node built-ins (`fs`, `path`, `url`).

**Depended on by:** All four models; `orderService.js` (for `getDatabase().transaction()`); `server.js`; `tests/helpers.js`.

## 7. Database Schema (ShopFlow)

Defined in [`shopflow-demo/src/db/schema.sql`](../shopflow-demo/src/db/schema.sql).

```
users (id PK, name, email UNIQUE, password_hash, role['customer'|'admin'], created_at)
  |─ 1:many ─> orders (id PK, user_id FK→users, status['pending'|'paid'|'refunded'], total_amount_cents, created_at)
                 |─ 1:many ─> order_items (id PK, order_id FK→orders CASCADE, product_id FK→products,
                 |                          product_name [snapshot], quantity, price_cents [snapshot])
                 |─ 1:0-or-1 ─> payments (id PK, order_id FK→orders UNIQUE, amount_cents,
                                          status['pending'|'succeeded'|'refunded'|'failed'],
                                          transaction_reference, created_at)
products (id PK, name, description, price_cents, stock, created_at)
  |─ 1:many ─> order_items.product_id
```

Indexes: `orders.user_id`, `order_items.order_id`, `payments.order_id`.

## 10. Summary of Findings

The workspace is a demonstration application built for an IBM hackathon. It has two conceptual layers:

**IMPACT (React SPA)** is a tool for software engineers to describe a proposed code change and see its predicted blast radius — affected files, risk scores, recommended tests, and release readiness. The UI is implemented as a client-side-only React 19 + Vite + Tailwind app. All "analysis" is performed by a deterministic mock engine (`mockAnalysisProvider.js`) that pattern-matches the change description to one of eight pre-defined ShopFlow scenarios sourced from a JSON ground-truth file. There is no backend server, no real AI call, and no persistent state in the React app today. The IBM Bob integration is stubbed and clearly marked.

**ShopFlow Demo API** is the analysis *target* — a realistic but small Node.js/Express e-commerce REST API with JWT authentication, a product catalog, transactional order creation with inventory reservation, and mock payment processing. It is a self-contained, runnable backend with a real SQLite database and a complete integration test suite. Its architecture is a clean, conventional layered stack: routes → controllers → services → models → SQLite.

The two sub-projects are loosely coupled: the React app reads ShopFlow's `change-impact-ground-truth.json` at build time to populate its scenario picker and simulate realistic analysis output, but neither project imports from the other at runtime. ShopFlow can be run and tested independently via `npm start` inside `shopflow-demo/`.
