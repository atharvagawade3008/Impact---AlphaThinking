## 1. Major Module-Level Dependencies

The ShopFlow backend follows a strict, unidirectional layered architecture. Modules at higher layers call modules at lower layers; no lower-layer module imports from an upper layer.

```
app.js / server.js          ← application bootstrap
    │
    ├── routes/*            ← HTTP surface (validation + auth guards + controller wiring)
    │       │
    │       ├── middleware/* ← cross-cutting: auth, validation, error handling
    │       │
    │       └── controllers/*  ← HTTP-to-service adapters (no business logic)
    │               │
    │               └── services/*   ← domain logic; only layer with cross-domain calls
    │                       │
    │                       ├── models/*         ← SQLite data access; no business logic
    │                       │       │
    │                       │       └── config/database.js  ← shared connection singleton
    │                       │               │
    │                       │               └── db/schema.sql  ← DDL resource (file read)
    │                       │
    │                       └── providers/mockPaymentProvider.js  ← external service stub
    │
    └── utils/errors.js     ← used by middleware AND services (bottom-up leaf)
    └── utils/jwt.js        ← used by authService AND authMiddleware (bottom-up leaf)
```

**Evidence:** `app.js` lines 2–7 contain the five route imports plus `errorMiddleware`. Each route file imports its corresponding controller. Each controller imports exactly one service. Each service imports the models it needs. All four models import `config/database.js`. No reverse-direction import was found in any file.

## 3. Route → Controller → Service → Model Relationships

### Authentication (`/api/auth`)

```
authRoutes.js
  router.post('/register', validateBody({name, email, password}), authController.register)
  router.post('/login',    validateBody({email, password}),        authController.login)
      │
      └─► authController.js
            .register → authService.register(request.body)        [response 201]
            .login    → authService.login(request.body)
                │
                └─► authService.js
                      .register:
                        userModel.findByEmail(email)              [duplicate check]
                        bcrypt.hash(password, 10)
                        userModel.create({name, email, passwordHash})
                        signToken(user)                           [jwt.js]
                      .login:
                        userModel.findByEmail(email)              [credential fetch]
                        bcrypt.compare(password, record.password_hash)
                        userModel.findById(record.id)             [public view, no hash]
                        signToken(user)                           [jwt.js]
                            │
                            └─► userModel.js → getDatabase() [users table]
```

**Evidence:** `authController.js` line 1 imports `authService`; `authService.js` lines 2–4 import `userModel`, `signToken`, `AppError`; `userModel.js` line 1 imports `getDatabase`.

## 4. Authentication Dependencies

The authentication system consists of four files with a clear two-phase structure: **token issuance** (register/login) and **token verification** (every protected request).

### Token Issuance Path

```
authRoutes.js  →  authController.js  →  authService.js  →  utils/jwt.js (signToken)
                                                         →  userModel.js (create / findByEmail)
                                                         →  bcryptjs (hash / compare)
```

- `authService.register` calls `bcrypt.hash(password, 10)` then `userModel.create(...)` then `signToken(user)`.
- `authService.login` calls `userModel.findByEmail(email)` to get the raw row (which includes `password_hash`), then `bcrypt.compare`, then `userModel.findById(record.id)` (to get the safe public view without the hash field), then `signToken(user)`.
- `signToken` in `utils/jwt.js` encodes `{ sub: user.id, role: user.role }` with `process.env.JWT_SECRET`.

**Key evidence:** `authService.js` line 9: `bcrypt.hash(password, 10)`. Line 11: `signToken(user)`. Line 16: `bcrypt.compare(password, record.password_hash)`. The raw `record` comes from `findByEmail` (which returns `SELECT *`, including `password_hash`); the subsequent `findById` (line 18) maps through `toUser()`, which deliberately excludes `password_hash`.

### Token Verification Path

```
userRoutes.js / orderRoutes.js / paymentRoutes.js
  router.use(requireAuth)
      │
      └─► authMiddleware.js
            verifyToken(token)          ← utils/jwt.js
            request.user = { id, role } ← written here, consumed by all controllers
```

- `authMiddleware.js` imports only `verifyToken` from `utils/jwt.js` and `AppError` from `utils/errors.js`.
- `verifyToken` calls `jwt.verify(token, secret())` and returns `{ id: Number(payload.sub), role: payload.role }`.
- The `request.user` object written here is the only mechanism through which a user's identity reaches controllers and services. Every protected controller reads `request.user.id` (e.g., `orderController.js` line 5: `request.user.id`).

**Critical contract:** The shape `{ id, role }` produced by `verifyToken` is consumed directly by `userController`, `orderController`, and `paymentController` without re-querying the database. Any change to `verifyToken`'s return shape propagates to all three controllers and all services they call with `userId`.

### Authentication is Not Re-Checked in Services

`userService`, `orderService`, and `paymentService` receive `userId` as a plain integer argument. They do NOT re-verify the token themselves. This means:

- If `authMiddleware.js` is bypassed or removed from a route group, services will run without any identity guarantee.
- `paymentService` additionally enforces ownership by checking `order.userId !== userId` (lines 8, 47) using `orderModel.findById` — this is the only in-service ownership guard.

## 5. Order → Product / Payment / User Dependencies

`orderService.js` is the most interconnected module in the codebase. It imports from four other modules and is the sole caller of `productService.reserveStock`.

### Order → User

```
orderService.createOrder(userId, items)
  └─► userService.getProfile(userId)    [line 10 — throws 404 if user missing]

orderService.listOrders(userId)
  └─► userService.getProfile(userId)    [line 40 — throws 404 if user missing]
```

**Purpose:** Guards both `createOrder` and `listOrders` against orphaned or invalid user IDs. If `userService` or `userModel` changes the definition of "valid user," these calls would reflect that change automatically.

**Evidence:** `orderService.js` lines 10 and 40.

### Order → Product

```
orderService.createOrder(userId, items)
  └─► productService.getProductById(productId)   [line 25 — price snapshot]
      └─► productModel.findById(productId)

  └─► [inside transaction] productService.reserveStock(productId, quantity)  [line 31]
      └─► productModel.decreaseStock(productId, quantity)
          UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?
```

Two separate calls are made for each product:
1. **Before the transaction:** `getProductById` to fetch the current price — this price is frozen in the order items as `priceCents`.
2. **Inside the transaction:** `reserveStock` to decrement `stock`. If any product has insufficient stock, `decreaseStock` returns `false`, `reserveStock` throws `AppError(409)`, and the SQLite transaction rolls back — including any stock decrements already applied to earlier items in the same order.

**Evidence:** `orderService.js` line 24–27 (price fetch), line 30–33 (transaction with `reserveStock`). `productModel.js` line 29–31 (`decreaseStock` conditional UPDATE using `AND stock >= ?`).

**Price-to-cents conversion:** `orderService` line 26: `priceCents: Math.round(product.price * 100)`. The model exposes `price` as a decimal (line 9 of `productModel.js`: `price: row.price_cents / 100`). The service converts it back to cents for order storage. This round-trip creates a precision dependency.

### Order → Payment

```
orderService.createOrder(...)
  └─► paymentService.preparePayment(order.id, userId)   [line 35 — after transaction]
      └─► orderModel.findById(orderId)                  [re-verifies ownership]
          paymentModel.findByOrderId(orderId)           [idempotency check]
          paymentModel.create({orderId, amountCents})   [creates pending payment]
```

`orderService` calls `paymentService.preparePayment` as the final step of `createOrder`, outside the SQLite transaction. The order is created and stock reserved before the payment row is inserted. If `preparePayment` fails, the order exists without a payment record.

**Evidence:** `orderService.js` line 34–35. `paymentService.js` lines 13–19 (`preparePayment`).

**Note:** `orderService` imports `paymentService`, but `paymentService` does NOT import `orderService`. `paymentService` calls `orderModel` directly to check order ownership and update order status. This is a deliberate asymmetry that avoids a circular import.

### Payment → Order (reverse write)

```
paymentService.processPayment(...)
  └─► orderModel.updateStatus(orderId, 'paid')     [line 39]

paymentService.refundPayment(...)
  └─► orderModel.updateStatus(orderId, 'refunded') [line 59]
```

`paymentService` writes back to the `orders` table through `orderModel` after both payment success and refund. The order's `status` field is the only persisted field updated by these calls. This creates a bidirectional data dependency between orders and payments at the database level, even though the import graph is one-directional.

## 6. Test Dependencies on Application Modules

### `tests/helpers.js` — Central Test Fixture

`helpers.js` is the test infrastructure root. All five test files import from it.

```js
// helpers.js lines 1–2: environment overrides (must run before any import)
process.env.SHOPFLOW_DB_PATH = ':memory:';
process.env.JWT_SECRET = 'test-secret';

// Dynamic imports (top-level await)
const { initializeDatabase, getDatabase } = await import('../src/config/database.js');
const { seedDatabase } = await import('../src/db/seed.js');
const { authService } = await import('../src/services/authService.js');
export const { default: app } = await import('../src/app.js');
```

**Direct imports in `helpers.js`:**
- `src/config/database.js` — `initializeDatabase` and `getDatabase` for schema creation and direct table truncation in `resetDatabase()`
- `src/db/seed.js` — `seedDatabase` called inside `resetDatabase()` to re-populate products
- `src/services/authService.js` — `authService.register` powers `createTestUser()`
- `src/app.js` — the Express app object passed to Supertest

The `process.env` overrides on lines 1–2 must run **before** any module is imported, because `config/database.js` reads `SHOPFLOW_DB_PATH` at connection time and `utils/jwt.js` reads `JWT_SECRET` lazily via the `secret()` function. Dynamic `await import(...)` ensures the env overrides are in place first.

### Individual Test File Dependencies

| Test file | Imports from helpers | Application surface exercised |
|---|---|---|
| `auth.test.js` | `app`, `resetDatabase` | `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/users/me`, `PUT /api/users/me` |
| `products.test.js` | `app`, `resetDatabase` | `GET /api/products`, `GET /api/products/:id` |

## 7. Reverse Dependencies (Impact of Changes)

The following are the relationships where a change to one module propagates to other modules, derived from actual import and call chains.

### R1: `utils/jwt.js` — affects `authService.js` and `authMiddleware.js`

`authService.js` imports `signToken`; `authMiddleware.js` imports `verifyToken`. Both are the only callers. A change to the JWT claims shape (e.g., removing `role`, renaming `sub`), the secret source, or the expiry default affects:
- All tokens issued (registration, login)
- All token validations (every request to `/api/users`, `/api/orders`, `/api/payments`)
- `request.user.id` and `request.user.role` in all three controller groups

**Affected tests:** `auth.test.js`, `orders.test.js`, `payments.test.js`, `integration.test.js` (all rely on tokens).

---

### R2: `middleware/authMiddleware.js` — affects `userRoutes.js`, `orderRoutes.js`, `paymentRoutes.js`

All three route files call `router.use(requireAuth)` at the top, making `requireAuth` the gate for every endpoint in those groups. A change to `requireAuth` — e.g., checking a role, adding a header requirement, or changing the `request.user` shape — silently affects every handler in those three route files without touching the controllers.

**Evidence:** `userRoutes.js` line 8, `orderRoutes.js` line 8, `paymentRoutes.js` line 8: all contain `router.use(requireAuth)`.

---

### R3: `utils/errors.js` — affects 8 files across 3 layers

`AppError` is consumed by all three middleware files and all five service files. The `errorHandler` in `errorMiddleware.js` uses `instanceof AppError` to decide whether to use `error.status` or default to 500. Changing `AppError`'s class name, constructor signature, or removing the `status` field would break:
- `errorMiddleware.js` (status selection logic, line 10)
- Every service's error propagation contract

---

### R4: `config/database.js` — affects all 4 models and `orderService.js`

All four models call `getDatabase()` on every operation (no local caching). `orderService.js` calls `getDatabase().transaction()` directly. A change to `getDatabase()`'s return type, connection configuration, or singleton behaviour affects all data access in the application.

The `connection` variable is module-level state (line 8). Between tests, `helpers.js` does not call `closeDatabase()` — it reuses the same `:memory:` connection across the full test run. Any change that resets this module-level state between calls would break the test isolation model.

---

### R5: `services/productService.js` — affects `services/orderService.js`

`orderService` imports `productService` for two purposes:
1. `getProductById(productId)` — price lookup at order creation time
2. `reserveStock(productId, quantity)` — inside the transaction

A change to `productService.getProductById`'s return shape (specifically the `price` field) would break the `priceCents: Math.round(product.price * 100)` line in `orderService.js` line 26. A change to `reserveStock`'s error semantics (e.g., returning instead of throwing on insufficient stock) would silently allow over-sale.

---

### R6: `models/orderModel.js` — affects both `orderService.js` and `paymentService.js`

`orderModel` is the only model imported by two services:
- `orderService.js` uses `orderModel.create`, `findById`, `findByUserId`
- `paymentService.js` uses `orderModel.findById` (ownership check) and `orderModel.updateStatus` (after payment + refund)

A change to `orderModel.findById`'s return shape — specifically `order.userId` or `order.status` or `order.totalAmount` — affects both services. `paymentService.js` line 8: `order.userId !== userId`; line 26: `order.totalAmount`. `orderService.js` line 46: `order.userId !== userId`.

---

### R7: `services/paymentService.js` — affects `services/orderService.js`

`orderService.createOrder` calls `paymentService.preparePayment` as its final step (line 35). The return value is spread directly into the response: `return { ...order, payment }`. If `preparePayment` changes its return shape or starts throwing in new cases, the `POST /api/orders` response shape and error behaviour change without any modification to `orderService` or `orderController`.

---

### R8: `db/schema.sql` — affects all 4 models and `paymentService.js`

`schema.sql` defines the column names, types, constraints, and allowed values that models depend on through raw SQL strings. No ORM mediates this — models embed SQL literals. Examples of direct coupling:
- `userModel.js` line 16: `INSERT INTO users (name, email, password_hash)` — column names hardcoded
- `orderModel.js` line 34: `INSERT INTO orders (user_id, total_amount_cents)` — column names hardcoded
- `paymentModel.js` line 18: `INSERT INTO payments (..., status) VALUES (?, ?, 'pending')` — the string `'pending'` must match the schema's `CHECK` constraint
- `paymentService.js` line 24: `order.status === 'refunded'` — tests a value constrained by `schema.sql`'s `CHECK (status IN ('pending', 'paid', 'refunded'))`

Changing a column name, an allowed status value, or a constraint in `schema.sql` requires matching changes in the model(s) that reference it.

---

### R9: `tests/helpers.js` — affects all 5 test files

Every test file imports `app` and `resetDatabase` from `helpers.js`. A change to `helpers.js` — e.g., a different test secret, a changed `resetDatabase` truncation order, or modifying `createTestUser`'s default credentials — affects all tests that depend on those exports. The dynamic import order (env vars set before modules load) is also load-order sensitive: if any test file imported a module before `helpers.js` set `SHOPFLOW_DB_PATH`, the real SQLite file would be opened instead of `:memory:`.

## 8. Highest-Impact Dependency Chains

The following chains represent the deepest or widest cascades, where a change at the top propagates through the most downstream consumers.

### Chain A — JWT contract (widest authentication blast radius)

```
utils/jwt.js (signToken / verifyToken / claims shape)
    │
    ├── authService.js (signToken called at register + login)
    │       └── authController.js → authRoutes.js → app.js
    │               └── tests: auth.test.js, integration.test.js
    │
    └── authMiddleware.js (verifyToken → request.user shape)
            └── userRoutes.js   → userController.js → userService.js
            └── orderRoutes.js  → orderController.js → orderService.js
            └── paymentRoutes.js → paymentController.js → paymentService.js
                    └── tests: auth.test.js, orders.test.js, payments.test.js, integration.test.js
```

A change to `utils/jwt.js` touches every protected endpoint and every test that uses tokens — 4 of 5 test files.

---

### Chain B — Order creation (deepest service fan-out)

```
POST /api/orders → orderController.create(request.user.id, items)
    │
    └── orderService.createOrder(userId, items)
          ├── userService.getProfile(userId)
          │       └── userModel.findById → getDatabase() [users]
          ├── productService.getProductById(productId) × N items
          │       └── productModel.findById → getDatabase() [products]
          ├── getDatabase().transaction()               ← direct db call
          │     └── productService.reserveStock × N items
          │               └── productModel.decreaseStock → getDatabase() [products]
          │     └── orderModel.create → getDatabase() [orders + order_items]
          └── paymentService.preparePayment(order.id, userId)
                  ├── orderModel.findById → getDatabase() [orders]
                  └── paymentModel.create → getDatabase() [payments]
```

A single `POST /api/orders` touches **5 services/models** and **4 database tables** (`users`, `products`, `orders`, `order_items`, `payments`) in a single request. Any change to `userService`, `productService`, `orderModel`, or `paymentService.preparePayment` can alter the outcome of order creation.

---

### Chain C — Payment → Order status write-back (cross-domain state mutation)

```
POST /api/payments → paymentController.process(orderId, amount, userId)
    └── paymentService.processPayment(...)
          ├── orderModel.findById(orderId)   [read orders]
          ├── paymentModel.findByOrderId + paymentModel.create/updateStatus [read+write payments]
          ├── mockPaymentProvider.processPayment() [external stub]
          └── orderModel.updateStatus(orderId, 'paid') [WRITE orders]

POST /api/payments/:id/refund → paymentController.refund(userId, paymentId)
    └── paymentService.refundPayment(...)
          ├── paymentModel.updateStatus(id, 'refunded', ref) [write payments]
          └── orderModel.updateStatus(orderId, 'refunded')   [WRITE orders]
```

`paymentService` is the only service that writes to a table "owned" by a different domain (`orders`). This bidirectional data coupling means a change to `orderModel.updateStatus`'s behaviour or the allowed status values in `schema.sql` requires reviewing `paymentService` as well as `orderService`.

---

### Chain D — `AppError` (broadest error contract)

```
utils/errors.js  (AppError class — status + message)
    │
    ├── authMiddleware.js     [throws 401 on bad token]
    ├── validationMiddleware.js [throws 400 on bad input]
    ├── errorMiddleware.js    [instanceof check — determines HTTP status]
    ├── authService.js        [throws 409 duplicate, 401 bad credentials]
    ├── userService.js        [throws 404 not found, 409 duplicate email]
    ├── productService.js     [throws 404 not found, 409 insufficient stock]
    ├── orderService.js       [throws 400, 404]
    └── paymentService.js     [throws 404, 409, 400]
```

`AppError` is the most universally imported local module (8 importers across 3 layers). The `errorHandler` in `errorMiddleware.js` relies on `instanceof AppError` to distinguish operational errors from unexpected ones. Any change to this class propagates to every error-signalling point in the application.

---

### Chain E — `config/database.js` (infrastructure foundation)

```
config/database.js (getDatabase singleton, initializeDatabase, schema.sql read)
    │
    ├── userModel.js   → getDatabase() on every method
    ├── productModel.js → getDatabase() on every method
    ├── orderModel.js  → getDatabase() on every method
    ├── paymentModel.js → getDatabase() on every method
    ├── orderService.js → getDatabase().transaction() directly
    ├── db/seed.js     → initializeDatabase() + getDatabase()
    ├── server.js      → initializeDatabase() at startup
    └── tests/helpers.js → initializeDatabase() + getDatabase() in resetDatabase()
```

The module-level `connection` singleton means the first caller to `getDatabase()` after process start opens the connection. In tests, `helpers.js` sets `SHOPFLOW_DB_PATH=:memory:` before any import runs, ensuring the singleton is initialised with an in-memory path. A change that makes `getDatabase()` non-singleton, or that alters when/how `schema.sql` is applied, would break both production startup and test isolation.
